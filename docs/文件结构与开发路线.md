## 1. 原版调研结论速览

### 1.1 UI 屏幕清单（从 AssetBundles 与精灵图反推）

原版每个 UI 模块一个 bundle，这本身就是一张"屏幕划分表"：

| Bundle / 精灵 | 屏幕 | 关键素材 |
|---|---|---|
| `ui-clicktoplay` / `15LANDS_*` | 标题画面（点击开始） | NewGame / Subscribe 按钮 |
| `ui-difficulty.*` | 难度选择 | |
| `ui-general` / `ui-headers` | 通用 UI 与标题栏 | |
| `map01_*.png`（带语言后缀） | **世界地图 / 信件墙**（关卡选择，信件按 `LPOSITION` 摆位） | |
| `dialog_bg_c/l/r*` + `PERSON.LETTER` | **读信**（每角色专属信纸背景，如 `letter_bg_ci`） | |
| 句子块 + `ruletag_*` + `BLOCKS.txt` | **排信**（字条上带规则标签图标：`0_3`/`x_1`/`conflict`…） | |
| `ranktagA/B/C/Bad` + `levelinformationrank_*` | **结局结算**（S/A/B/C/Bad 评级标签） | |
| `information_window_*ending*.png` | **结局图鉴**（完成/未完成/选中三态） | |
| `ui-achievements` + `achievements_icon_*` | **成就系统**（含结局/相册/文档收集图标） | |
| `cg-*.bundle` + `ALBUM.txt` | CG 演绎与相册（`EV001` 等分组） | |
| `ui-dictionary` + `DOCUMENTS.txt` | 文档图鉴（角色相关文档收集，`FNB` 分类） | |
| `spines.bundle` | 角色 Spine 动画（`PERSON.FIG` 引用） | |
| `sounds` / `sounds-mu` / `sounds-helps` | 音效 / 音乐 / 提示音 | |

**结论**：原版屏幕 = 标题 → 难度 → 信件墙 → 读信 → 排信 → 结算 → 图鉴（结局/相册/文档/成就）。
我们的场景划分应与之对齐（见第 4 节对照表）。

### 1.2 原版数据组织方式

```
leveldata-retail.bundle   每关一个 JSON（0001.json~0071.json 共 63 关）
                          + LEVELS.txt（关卡索引数组）+ BASICDATA.txt（LEVELCOUNT、PERSON 角色主题表）
data.bundle               DIALOG（规则库 + 剧情分镜 PACK + 教学计数）
                          PROFILES（角色档案：TRIGGER/CONDITION 解锁）
                          BLOCKS（句子 ID → 规则标签）
                          ALBUM / ACHIEVEMENTS / DOCUMENTS / BGM / MUSICS / ICONS / DECORATIONS
localization.bundle.*     全部文本在 strings.po（gettext，CONTENT_ID → msgctxt）
```

四个关键设计模式：

1. **每关一个 JSON**，索引与基础配置分离——加关不加代码，天然支持 DLC 式增量分发。
2. **文本与数据分离**：关卡 JSON 只存 `CONTENT_ID`，正文全在 `.po`——一次内容、多语言。
3. **角色主题集中配置**（`PERSON`）：每个角色一套配色/信纸/窗口色
   （`FIG_COLOR`/`BG_COLOR`/`LETTER`/`WINDOW_COLOR`）——对应我们关卡 JSON 里的 `characters` 表，应移出为全局档案。
4. **收集系统数据化**（ALBUM/ACHIEVEMENTS/DOCUMENTS）——图鉴不是 UI 特例，而是可配置的数据。

### 1.3 原版核心机制三件套（与我们的映射）

| 原版机制 | 说明 | 我们的现状 / 映射 |
|---|---|---|
| **句子三型** | TYPE 0 固定句（首尾，不可动）；TYPE 1 可排序句；TYPE 2 **条件句**（平时隐藏，结局 `REPLACE` 时才登场替换原句） | 黑块 ≈ TYPE 0；字条 ≈ TYPE 1；**条件句尚未实现**——这是"蝴蝶效应"的载体，必须补 |
| **结局 = CHANGE 指令序列** | 结局携带 `RANK`（S~Bad/Z）+ `REP`（声望 325/131/52/21/8/3/0 对数递减）+ `CHANGE` 数组（`REPLACE` 替换句子 / `DRA` 删除句子） | 现有"执行按钮只打印序列"；架构设计.md 的 `outcomes.verdicts(fate/flag)` 简版被此机制**取代** |
| **条件表达式引擎** | `SS(A,B)` 排序、`OS/OSS/S` 相邻、`IN(L/R/M,X)` 跨行位置、`&&/||/!` 布尔、条件句触发标记；跨关 `CURRENT/ELLE/SRANK/STORY/READ/ACHIEVE`；`FILTER/FALLBACK` 回退。**CONDITION 与 UNLOCK 共用同一引擎** | `get_sequence_ids()` 输出完整序列 = 引擎的求值上下文；但匹配方式从"全序列相等"改为**表达式求值**（原版只判相对顺序/位置，不判完整序列） |

其他值得借鉴：`LPREVIOUS` 通信线接续（一行信接续历史某行）、`LPOSITION` 信件墙布局、
`LIMIT/LIMITDESC` 规则教学（新规则先展示再约束）、`ROWCOUNT` 行数数组化（单行只是特例，三行关卡 0048 存在）。

**求值三表**（引擎全部状态）：合并序列（所有句子当前顺序）+ 触发状态表（条件句）+ 世界状态表（跨关结局历史/声望/成就）。

## 2. 设计决策（8 条）

| # | 决策 | 理由 |
|---|---|---|
| D1 | **每关一个 JSON**（`data/levels/0001.json`）+ `levels_index.json` 索引，取代"day 数据包" | 对齐原版；加关不加代码；4 位编号便于排序与扩展 |
| D2 | **文本进 `locales/*.po`**，JSON 存 `text_key`；`text` 内联字段作为早期兜底（加载器优先 `text`，其次 `tr(text_key)`） | 原版模式；Godot 原生支持 `.po` + `tr()`；原型期不想维护 po 就内联，之后无痛迁移 |
| D3 | **行数数组化**：`rows: [L, R, M?]`，单行是长度为 1 的特例 | 原版 ROWCOUNT=1/2/3；不做 1/2/3 行分别建模 |
| D4 | **句子三型进 Schema**：`blocks`（TYPE 0 固定）/ `strips`（TYPE 1 可排序）/ `variants`（TYPE 2 条件句，挂靠在 base 句下） | 词汇沿用现有的"黑块/字条"，语义对齐原版 |
| D5 | **结局 = `endings` 字典 + `CHANGE` 数组 + `RANK/REP`**；`conditions` = 表达式数组**按序匹配、首个命中**，带 `filter/fallback` | 取代 架构设计.md 的"condition 全序列相等 + verdicts 简版" |
| D6 | **`ConditionEngine` 独立成模块**（分词→递归下降→求值），`RuleEngine` = 用 ConditionEngine 判结局 + 应用 CHANGE + 写世界状态。UNLOCK 复用同一引擎 | 引擎一次实现，判定与解锁两处使用（原版做法） |
| D7 | **GameState 增世界状态表**：`history: {level_id: {row_index: ending_id}}` + `total_rep` + 已读/已解锁/已收集集合 | 跨关剧情（CURRENT/ELLE）的数据底座 |
| D8 | **角色档案全局化**：`data/characters.json`（name/color/信纸背景/主题色），从关卡 JSON 移出 | 对齐原版 PERSON；多个关卡共用同一角色配置 |

对 `架构设计.md` 的修订：第 3 节（GameState/GameFlow/RuleEngine 三轴）、第 4 节（场景星型路由与循环）
**继续有效**；第 5 节 Schema 被本文档第 5 章修订；第 8 节路线被本文档第 7 章取代。

设计要点：

- **场景文件夹自包含**：一个屏幕的 `.tscn` 与专属脚本放同一目录（Godot 惯例，F6 单跑时路径直观）；
  跨场景共享的代码才进 `scripts/`。
- **`data/` 是内容层、`scenes/` 是视图层、`autoload/` 是状态层**——三层互不越界：
  场景不写死数据路径（走 GameState），数据不含 UI 信息（LPOSITION 除外，它是信件墙的布局数据）。
- **`.po` 与 Godot 的 `tr()` 天然兼容**，`text_key` 命名沿用原版的点分命名空间（`关卡id.句子id`）。
- **`legacy` 文件不迁入**，直接删除（见第 6 节）。

## 5. 数据 Schema v2（每关一个 JSON）

### 5.1 关卡文件 `data/levels/0001.json`

```json
{
  "level_id": "0001",
  "title": "黑伞",
  "row_count": 2,
  "unlock": "",

  "rows": [
    {
      "id": "L",
      "character": "A",
      "position": "0,3",
      "previous": "start",
      "blocks": [
        { "id": "PanelA1", "text_key": "0001.PanelA1", "text": "　　下午六点，暴雨倾盆。…" }
      ],
      "strips": [
        { "id": "A1", "text_key": "0001.A1", "text": "外面下着暴雨，我出门带上了黑伞。" }
      ],
      "variants": [
        { "id": "A2_1", "base": "A2", "text_key": "0001.A2_1" }
      ]
    },
    { "id": "R", "character": "B", "position": "0,6", "previous": "start",
      "blocks": [], "strips": [], "variants": [] }
  ],

  "endings": {
    "S1":   { "rank": "S",   "rep": 325, "change": [ { "type": "REPLACE", "data": "A2_1" } ] },
    "BAD1": { "rank": "Bad", "rep": 0,   "change": [] }
  },

  "conditions": [
    { "expr": "SS(A1,B1)&&IN(L,A2)", "ending": "S1" },
    { "expr": "", "ending": "BAD1", "fallback": true }
  ]
}
```

### 5.2 字段说明

| 字段 | 含义 | 与原版对应 |
|---|---|---|
| `level_id` | 4 位字符串编号 | `LEVELID` |
| `title` | 关卡名（信件墙显示） | — |
| `row_count` | 行数（可从 rows 推导，保留便于快速判断） | `ROWCOUNT` |
| `unlock` | 解锁条件表达式（空 = 初始解锁）；与 conditions 共用同一表达式语法 | `UNLOCK` |
| `rows[].id` | 行标识：`L` / `R` / `M`（三行时） | 字段族前缀 |
| `rows[].character` | 本行默认角色（引用 `characters.json` 的 id） | `LNAMECODE` |
| `rows[].position` | 信件墙布局 `"列,行"` | `LPOSITION` |
| `rows[].previous` | 通信线接续：`"start"` 或 `"0002:L"`（本行是那行的下一封） | `LPREVIOUS` |
| `rows[].blocks[]` | 固定句（黑块，TYPE 0）：不可拖，首尾框架 | `TYPE 0` |
| `rows[].strips[]` | 可排序句（字条，TYPE 1）：玩家拖拽重排 | `TYPE 1` |
| `rows[].variants[]` | 条件句（TYPE 2）：**不进初始界面**；结局 REPLACE 时替换 base 句 | `TYPE 2` |
| `endings{}` | 结局字典：`rank`（S/A/B/C/D/E/Bad/Z）+ `rep`（325/131/52/21/8/3/0 对数递减）+ `change` 指令序列 | `LENDING` |
| `change[]` | `REPLACE`（用 variants 句替换同 base 句）/ `DRA`（删除句子）；数组可组合 | `CHANGE` |
| `conditions[]` | 按序匹配、首个命中生效；`expr` 为空 + `fallback:true` = 兜底坏结局 | `CONDITION` |
| `text_key` / `text` | 文本引用（`.po` msgctxt）/ 内联兜底，二选一填 | `CONTENT_ID` |

### 5.3 条件表达式语法（v1 范围）

| 函数 | 语义 |
|---|---|
| `SS(A,B[,C])` | A 在 B（在 C）之前（严格顺序链） |
| `OS(A,B)` / `OSS(A,B)` / `S(A,B)` | A 紧邻 B 前 / 相邻不分序 / 相邻 |
| `IN(L,X)` / `IN(R,X)` / `IN(M,X)` | X 位于左行 / 右行 / 中缝 |
| `X` / `!X` | 条件句 X 已触发 / 未触发 |
| `&&` / `||` / `!` / `()` | 布尔运算 |
| `SRANK(0001)` | 0001 关达成 S 评价（跨关，阶段 E 接入） |
| `CURRENT(0002,0,S1)` / `ELLE(...)` | 历史结局点判定 / 集合判定（阶段 E 接入） |

**求值上下文三表**（引擎内部）：合并序列（L/R/M 各行 + 中缝的完整顺序）、
触发状态表（variants 已触发集合）、世界状态表（`GameState.history` + `total_rep`）。
`FILTER/FALLBACK`（同排序不同历史 → 不同结局）在 v2 预留字段 `filter`/`fallback`，阶段 E 接入。

### 5.5 与旧 Schema（架构设计.md 第 5 节）的差异

| 旧 | 新 | 原因 |
|---|---|---|
| day 数据包（一份 JSON 含 letters+columns+outcomes） | 每关一个 JSON + 索引 | 对齐原版，增量分发 |
| `letters[].pages` 独立信件文本 | 信 = 各行句子的初始序列（读信即读初始序列） | 原版方式，文本只存一份；如仍要散文式开场信，可加 `intro` 字段单列 |
| `outcomes[].condition` = 完整序列精确匹配 | `conditions[]` 表达式按序求值 | 原版只判相对顺序/位置；完整序列只是求值上下文 |
| `verdicts(fate/flag)` | `rank/rep` + 世界状态表 `history` | 原版声望制；跨关判定靠历史结局记录 |
| `columns` 两栏 | `rows[]` 数组（含中缝 M 落点） | 支持三行；**ArrangeBoard 需增加"中缝"合法落点**（原版 IN(M,X) 的 UI 基础） |

## 9. 一句话总结

> 原版告诉我们三件事：**内容即数据**（每关一个 JSON + .po 文本 + 角色档案）、
> **结局是"改写"不是"评分"**（CHANGE 指令让同一封信变成不同故事）、
> **历史是网状剧情的地基**（世界状态表 + 一套表达式引擎通吃判定与解锁）。
> 我们的文件结构为这三件事各留一个位置：`data/`、`scenes/performance/`、`scripts/core/condition_engine.gd` + `GameState.history`。
