# 添加新关卡与新人物指南

> 面向本项目（Godot 复刻《WILL：美好世界》）的内容作者。
> 关卡与角色**纯数据驱动**：加关卡 / 加人物一般只改 JSON 和贴图，不需要碰代码。
> 深度字段语义另见 `docs/数据Schema详解-关卡设计.md`（原版 63 关分析）与 `docs/0001关卡字段说明.md`；
> 地图演出规则见 `docs/选关界面-关卡地图与生长逻辑-Godot实现.md`。
> 解析代码：`scripts/core/level_data.gd`（Schema）、`scripts/core/condition_engine.gd`(表达式)。

## 0. 文件地图

| 文件 | 作用 |
|---|---|
| `data/characters.json` | 角色档案（id → 名字 / 颜色 / 头像路径） |
| `data/levels/levels_index.json` | 关卡索引：`levels` 数组登记全部关卡 id，`start` 为入口关 |
| `data/levels/<id>.json` | 单个关卡数据（行 / 句子 / 结局 / 判定 / 解锁） |
| `data/levels/<id>.txt` | 可选：剧情文本表（PO 格式，与 JSON 同名同目录） |
| `assets/header/header_<id>_2.png` | 角色人物栏图（444×132，解锁后显示） |

## 1. 添加新人物

### 1.1 步骤

1. **放头像**：`assets/header/header_<新id>_2.png`，建议 444×132。
   当前 `scenes/map/map.gd` 按 `header_%s_2.png` 硬编码加载这张图。
2. **登记档案**：在 `data/characters.json` 末尾加一项：

```json
"alicia": {
    "name": "艾丽西亚",
    "color": "#5a4a8a",
    "letter_bg": "res://assets/example/letter_bg_carlos.png",
    "header": "res://assets/header/header_alicia_2.png",
    "header_locked": "res://assets/header/header_alicia_0.png"
}
```

   - `color`：该角色剧情竖线 / 关卡块的颜色，`#rrggbb`；
   - `header` / `header_locked` / `letter_bg`：目前代码**尚未读取**（预留字段，对齐原版数据结构），放了不报错；
   - JSON 里 `name`、`color` 是地图实际使用的字段。
3. **在关卡里使用**：某关 `rows[].character` 写这个 id（见 §2）。

不需要改任何代码，也不需要在地图上"摆位置"。

### 1.2 地图上的表现（自动）

- **列位置**：按 `characters.json` 的书写顺序从中间向两侧拓展——
  第 0 个角色居中，第 1 个在右一列，第 2 个在左一列，第 3 个在右二列……每列宽 444。
- **隐藏直到解锁**：角色没有任何"可生长信件"时，人物栏里完全不显示；
  该角色的第一封信进入可生长状态（点信箱会出现）时，头像才整张出现。
  所以"只加人物不写信"在地图上看不到任何东西，这是设计行为。
- 每个已显示角色有一条本角色色的竖直剧情线，关卡块挂在自己的线上。

### 1.3 版权提醒

`assets/` 下现有人物图来自解包素材，仅作占位与机制参考；**公开发布前必须替换为原创图**，
尺寸保持 444×132 即可，文件名规则不变。

## 2. 添加新关卡

### 2.1 步骤

1. 新建 `data/levels/<id>.json`（id 惯例 4 位递增，如 `"0003"`，须与文件名一致）。
2. 在 `data/levels/levels_index.json` 的 `levels` 数组里追加 `"<id>"`，并在 `positions` 表里给每个新行指定**绝对栅格坐标**（§2.3 布局规则）。
   （地图的父子树靠每行的 `previous` 建立，与数组顺序无关；`start` 一般不动。）
3. 句子文本二选一：JSON 内联 `"text"`，或 `"text_key"` + 同名 `.txt` 文本表（§2.5）。
4. 编辑器直接运行，点信箱看生长；或用 §4 的冒烟脚本。

### 2.2 完整示例（单行关，仿 0002）

```json
{
    "level_id": "0003",
    "title": "新关卡名",
    "subtitle": "神啊，……（角色呼喊语）",
    "row_count": 1,
    "unlock": "ELLE(0002,L,S1,BAD1)",

    "rows": [
        {
            "id": "L",
            "character": "jz",
            "position": "2,4",
            "previous": "0002:L",
            "pendings": ["0001:R(S1)"],
            "blocks": [
                { "id": "PanelD1", "text": "（固定句 1，顶部框架块）" },
                { "id": "PanelD2", "text": "（固定句 2，底部弹性块）" }
            ],
            "strips": [
                { "id": "D1", "text": "可排序字条 1。" },
                { "id": "D2", "text": "可排序字条 2。" }
            ],
            "variants": [
                { "id": "PanelD2_1", "base": "PanelD2", "text": "S 结局替换后的条件句。" }
            ]
        }
    ],

    "endings": {
        "S1":   { "rank": "S",   "rep": 300, "change": [ { "type": "REPLACE", "data": "PanelD2_1" } ] },
        "BAD1": { "rank": "Bad", "rep": 0,   "change": [] }
    },

    "conditions": [
        { "expr": "SS(D1,D2)", "ending": "S1" },
        { "expr": "", "ending": "BAD1", "fallback": true }
    ]
}
```

### 2.3 字段说明

**顶层**

| 字段 | 说明 |
|---|---|
| `level_id` | 必须等于文件名（不含 `.json`） |
| `title` | 关卡名：地图细节卡的大字 |
| `subtitle` | 角色呼喊语（读信 / 演绎用） |
| `unlock` | 解锁表达式（§3）。空串 = 游戏开始就可生长 |
| `endings` | 结局表。**键顺序 = 细节卡上结局方块的排列顺序**；`rank` 评级名、`rep` 声望、`change` 见下 |
| `conditions` | 判定表，**按序匹配、首个命中**。最后一条惯例 `expr: ""`（恒真）+ `fallback: true` 兜底 |

`endings[].change` 条目：

- `{ "type": "REPLACE", "data": "<variant_id>" }` —— 该结局下 `base` 句被条件句替换；
- `{ "type": "DRA" 或 "D", "data": "<句子id>" }` —— 该结局下删除此句。

**rows[]（一行 = 一封一个角色的信）**

| 字段 | 说明 |
|---|---|
| `id` | `"L"` / `"R"`（三行关才用 `"M"`）。同一关两行 = 同一封信的两侧 |
| `title` | **本行自己的故事标题**（横向相连的多个块各起各的标题；缺省用关卡 `title`） |
| `character` | 角色 id，引用 `characters.json` |
| `position` | `"泳道,距离"`。**仅当该行未在 levels_index.json 的 positions 里登记时**作为自动布局回退：距离 = 相对父节点向下的生长增量，1 单位 = 80px；泳道目前不用 |
| `previous` | 实线父边：`"start"`（信箱）或 `"<关卡id>:<行id>"`（如 `"0001:L"`）。父关**达成过任意结局**后本行才可生长 |
| `pendings` | 待定边（虚线），形如 `["0001:R(S1)"]`，括号内为要求的结局集合，多条用 `&` 连接或数组多项。地图用 `dotted_lines_*` 素材绘制：`from` 已 reveal、本节点未 reveal 且评级条件达成时显示 |
| `blocks` | 固定句（黑块，TYPE 0）。`blocks[0]` = 顶部框架，最后一项 = 底部弹性块 |
| `strips` | 可排序句（字条，TYPE 1），玩家重排的对象 |
| `variants` | 条件句（TYPE 2）：`{id, base, text/text_key}`，结局 REPLACE 时替换 `base` |

**地图布局规则**（写 `positions` / `previous` 时要知道的）：

- **手动栅格（推荐）**：`levels_index.json` 的 `positions` 表，key = `"<关卡id>:<行id>"`，value = 绝对栅格坐标 `[gx, gy]`。`gx` 以半列宽 222px 为一格（0 = 地图中心列，**偶数 gx = 角色列轴线**，奇数 = 两列之间），`gy` 以 80px 为一格（从地图顶头像底边起算）。手动登记的节点不参与自动对齐，摆哪就在哪；
- **连线自动路由**：父子块间由 `map_route.gd` 用管件素材自动拼线——同列竖直直线、同高横线、跨列 S 弯（先竖→拐角→横向→拐角→竖），即"新信先横着拐个弯再往下走"；同一封信的 L/R 两行建议摆齐（gy 相同），齐平且角色不同时两块之间画**红色实线**；
- **自动布局（回退）**：未登记的节点深度 = 沿 `previous` 链累加 `distance`；同一封信的 L/R 两行自动**水平齐平**（浅者下移，其子树整体随移）；横向位置 = 该角色的人物列（§1.2）；
- `previous` 指向的父节点必须最终能放置（父链通到 `start`），否则控制台警告「节点无法放置」。

### 2.4 句子文本：内联 vs 文本表

- 内联：句子对象里直接写 `"text": "……"`（0002 的写法，写小关卡最快）；
- 文本表：句子对象写 `"text_key": "0003_D1"`，正文放 `data/levels/0003.txt`（PO 格式，0001 的写法）：

```po
msgctxt "STRINGS.DIALOG.CONTENT.0003_D1"
msgid ""
msgstr "正文第一行[br]\n"
"续行。"
```

  加载器取 `msgctxt` 最后一个点分段作为 key；`[br]` = 换行；相邻引号串自动拼接；
  两者都给了时 `text` 优先；都找不到时屏幕上原样显示 key，便于一眼发现漏配。

### 2.5 双行关要点

- 两行 `id` 分别 `"L"` / `"R"`，`character` 不同 → 地图上出现一对齐平块 + 红线；
- 两行的 `previous` 可以不同（各接各的父链）；
- `conditions` 的表达式可以混引两行句子 id（如 `SS(A2,B1)`），实现"一侧排序影响另一侧结局"；
- **交换纸条界面自动用双列模板**：`row_count ≥ 2` 即进入双列布局（两侧立绘 + 两列等宽字条 + 中缝跨行拖放），
  模板保存在 `templates/双列交换纸条模板.tscn`（即 `scenes/arrange/arrange_board.tscn` 的双列形态），
  新故事无需任何配置；需要单独复制模板做新场景时直接以它为基底。

## 3. 条件表达式速查

用于 `unlock` 与 `conditions[].expr`。逻辑运算：`&&` `||` `!` `( )`。空串 = 无条件命中。

**信内判定函数**（参数为句子 id；`merged` = 各行按行序拼接的当前序列）：

| 函数 | 含义 |
|---|---|
| `SS(A,B[,C])` | A 在 B（在 C）之前，严格顺序链 |
| `OS(A,B)` | A 紧邻 B 之前 |
| `OSS(A,B)` 或 `S(A,B)` | A、B 相邻（不分前后） |
| `IN(L/X)` 等：`IN(L,A)` | 句子 A 当前位于左行（`R` 右行 / `M` 中缝） |
| 裸标识符 `PanelD2_1` | 该条件句已触发（被 REPLACE 出场） |

**跨关函数**（`unlock` 里查世界状态；行号参数目前忽略，只查关卡级历史）：

| 函数 | 含义 |
|---|---|
| `CURRENT(0001,L,S1)` | 0001 关达成过 S1 |
| `ELLE(0001,L,S1,BAD1)` | 0001 关达成过 S1 或 BAD1（任一） |
| `SRANK(0001)` | 0001 关拿过 S 评级 |
| `READ(0001,1)` | 0001 关第 1 行（0 起）已读 |
| `STORY(x)` / `ACHIEVE(a,b)` | 剧情标记 / 成就（预留） |

示例：`"unlock": "ELLE(0001,L,S1,BAD1) && !SRANK(0002)"`。

## 4. 验证与调试

1. **编辑器直接运行**（F5）：点信箱 → 新节点应「线生长 0.5s → 块弹出」；点块 → 细节卡（关卡名 + 结局方块）；再点进读信。
2. **headless 冒烟**（不占编辑器，改完跑一遍最稳）：

   ```bash
   timeout 25 <godot.exe> --headless --path . res://tools/map_smoke_test.tscn
   ```

   全绿应见 `SMOKE PASS`；关注 `aligned_0001=true`、`rail_anchor_ok=true` 等行。
3. **视觉自检 + 截图**：`res://tools/map_visual_test.tscn` 会自动走两轮生长并开卡，配合仓库根的 `tmp_snap.ps1` 截屏对照。
4. **状态不存档**：`GameState`（`history` / `revealed_nodes` 等）目前纯内存，重开游戏即重置，方便反复看生长演出；
   想模拟"已通关某结局"，参照测试脚本直接写 `GameState.history["0001"] = ["BAD1"]`。
5. **常见报错**：
   - `无法打开关卡数据 / 数据解析失败` —— JSON 语法错或文件名 ≠ `level_id`；
   - `节点无法放置(父节点缺失?)` —— `previous` 链断了；
   - `ConditionEngine: 未知函数 XX` —— 表达式函数名拼错（大小写敏感）。

## 5. 自查清单

- [ ] `<id>.json` 已登记进 `levels_index.json` 的 `levels`，且每行在 `positions` 表里有坐标（key 与 `关卡id:行id` 完全一致）；
- [ ] 每行 `character` 存在于 `characters.json`（新人物已加档案 + 头像）；
- [ ] `positions` 里 `gx` 用偶数对齐该行角色列（角色列 = 按 `characters.json` 书写顺序从中心向两侧交替：yf=0、qyy=+2、jz=-2…），双行关两行 `gy` 相同（齐平出红线）；
- [ ] `previous` 链最终通到 `start`，且父关的解锁/结局条件真实可达成（避免死锁）；
- [ ] `conditions` 末条是空表达式兜底；
- [ ] 未登记 positions 的自动行：双行关两行 `position` 的第二个数想清楚谁深谁浅（浅的会被自动下移齐平）；
- [ ] 句子文本内联或文本表二者居其一，`text_key` 与 `.txt` 的 key 完全一致；
- [ ] 冒烟测试通过。
