## 二、核心技术发现：bundle「加密」之谜

### 2.1 现象

所有 `.bundle` 文件头部都是乱码，没有标准的 UnityFS 签名：

```
fonts-hans.bundle:  v_l%%k)h'y>upF8y...
data.bundle:        +*2Lt7it...
```

但注意一个细节：所有 `localization.bundle.*` 语言包的密文开头**完全相同**——这暗示加密是确定性的，或另有玄机。

### 2.2 分析过程

1. **静态分析 DLL**：在混淆过的 `Assembly-CSharp.dll` 中找到加密相关字符串（`RijndaelManaged`、`CipherMode`、`CreateDecryptor`、`TransformFinalBlock`、`MD5`、`SHA256` 等），一度以为 bundle 被 AES/Rijndael 加密。

2. **自写 IL 反汇编器**：由于环境无 .NET 工具且 GitHub 不通，用 Python `dnfile` 库自写了一个 IL 字节码反汇编器，解析混淆后的方法体，定位到 5 个「解密方法」（模式均为：`RijndaelManaged → set_Key(静态字段) → set_Mode → set_Padding → CreateDecryptor → TransformFinalBlock`）以及密钥推导链：
   ```
   密钥 = SHA256(UTF8(字符串))
   ```

3. **穷举验证失败**：用全部 2769 个候选字符串做 SHA256 密钥 + AES-256-ECB 解密 bundle 头，无一命中 —— 说明方向有误。

4. **突破口**：发现类型 `AssetBundleManager` 及其方法名**未被混淆**（这是 Unity 官方 AssetBundleManager 插件的修改版）。其中 `OffsetFromFilename` 方法揭示了真相：

   ```csharp
   // 反汇编还原的伪代码
   offset = (Abs(Hash(文件名)) % 373) + 167;
   ```

   而 bundle 加载调用的是：
   ```csharp
   AssetBundle.LoadFromFileAsync(path, 0, OffsetFromFilename(name));
   ```

### 2.3 真相

**bundle 根本没有被加密。** 每个 `.bundle` 文件前面被塞入了 `(Abs(hash(文件名)) % 373) + 167` 字节（约 167~539 字节）的垃圾数据，游戏通过 Unity 的 `offset` 参数跳过垃圾区直接读取真正的 bundle。这是开发者故意设置的反解包障眼法。

哈希算法（复刻自 IL，注意 C# int32 溢出语义）：
```python
def hash33(s):
    h = 0
    for ch in s:
        h = (h * 33 + ord(ch)) & 0xFFFFFFFF   # C# int 回绕
    return h - 0x100000000 if h >= 0x80000000 else h

offset = (abs(hash33(归一化文件名)) % 373) + 167
```

**踩过的坑——文件名归一化**：`OffsetFromFilename` 会先对文件名做变换：
1. `ToLower`
2. 去掉最后一个扩展名（如 `localization.bundle.cmn-hans-cn` → `localization.bundle`）
3. 若结果仍含 `.`，再剥一层（→ `localization`），并重新拼接 → **`localization.bundle`**

因此 `localization.bundle.cmn-hans-cn` 实际按 `localization.bundle` 算哈希——这也解释了为什么所有语言包密文开头完全相同（它们共用同一个偏移 174）。

## 三、提取工具

保留在游戏根目录：`extract_bundles.py`

```bash
# 提取全部 bundle
python extract_bundles.py

# 提取指定 bundle
python extract_bundles.py fonts-hans.bundle localization.bundle.cmn-hans-cn
```

工具自动完成：偏移计算 → 校验 UnityFS/CAB 头 → UnityPy 解包 → 按类型分类导出。

## 四、环境问题与解决

| 问题 | 解决 |
|---|---|
| pip 安装报 SSL 错误（`check_hostname requires server_hostname`） | 旧版 pip 21.2.4 的 bug，先 `python -m pip install --upgrade pip` 升级到 26.x |
| GitHub 不通，无法下载 AssetStudio/dnSpy | 改用纯 Python 方案：`dnfile`（元数据解析）+ 自写 IL 反汇编器 |
| dnfile 0.18 API 变化 | `MethodBodyReader` 已移除需自实现方法体读取；`MethodList` 是成员索引列表而非 start/end 对 |
| UnityPy 1.25 API 变化 | `Font.m_FontData` 是 `List[int]`；`TextAsset` 为 UTF-16LE 文本；`AudioClip.samples` 值为 bytes |
| 语言包文本互相覆盖 | 文本按 bundle 完整文件名分目录保存 |

## 五、遗留限制

1. **中文纹理字体无法还原 TTF**：打包时已栅格化，只能使用图集 PNG
2. **部分 Texture2D 无法导出**：个别 bundle（如 fonts-hang）的纹理数据字段在 UnityPy 1.25 下解析不完整（`m_StreamData` 为空），如需可换 AssetStudio 尝试
3. **DLL 中 5 个 Rijndael 方法的真实用途**：经分析是游戏存档文件的加解密（`ReadAllBytes → 解密 → Deserialize` 流程），与 bundle 无关；`strings.po` 等文本未加密

## 六、工作流程回顾

```
1. 识别引擎（Unity 2017.4.5f1）
2. 发现 bundle 头部异常（疑似加密）
3. 反汇编混淆 DLL → 找到 SHA256 密钥推导 + Rijndael 解密方法
4. 穷举密钥失败 → 转向未混淆的 AssetBundleManager
5. 发现 OffsetFromFilename → 破解「垃圾前缀」真相
6. 修复双扩展名归一化 → 全部 bundle 头部验证通过
7. UnityPy 适配提取 → 28 字体 / 413 音频 / 1337 精灵 / 843 纹理 / 117 文本
8. 输出分类整理 + 工具脚本保留
```
