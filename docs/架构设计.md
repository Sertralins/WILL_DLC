# 《WILL:美好世界》复刻 — 整体架构设计

> 本文档是宏观架构指导：在已完成的两个场景（信件阅览 `scenes/letter/letter_reader.tscn`、交换字条 `scenes/arrange/arrange_board.tscn`）之上，
> 规划后续所有场景与系统的搭建方式。重点是**场景之间的关联**与**数据流的走向**。
>
> 配套文档：`README.md`（已有功能与实现原理详解）。

---

## 1. 总体判断：核心玩法已成立，缺的是"脊椎"

现有两个场景质量不错——拖拽的占位预览、边缘吸附、看门狗兜底都是原版没有的细节。
但目前它们是**两个孤岛**：

| 问题 | 现状位置 |
|---|---|
| 两个场景各硬编码各的 JSON 路径，彼此不认识 | `scripts/ui/letter/letter_reader.gd` 的 `LETTER_PATH`、`scripts/ui/arrange/arrange_board.gd` 的 `LEVEL_PATH` |
| 场景跳转写死在场景内部 | `scripts/ui/letter/letter_reader.gd` 末尾 `change_scene_to_file("res://scenes/arrange/arrange_board.tscn")` |
| 字条排列顺序只存在于场景树里，切场景即丢失 | `scripts/ui/arrange/arrange_board.gd` 的 `get_sequence_ids()` 现读现算 |
| 执行按钮只打印序列，判定/结算/下一天全部空缺 | `scripts/ui/arrange/arrange_board.gd` 的 `_on_execute_pressed()` |
| 同一段故事（黑伞）在 `letter_1.json` 与 `level_1.json` 各存一份文案 | `data/` 目录 |

《WILL》的全部价值在**循环**上：读信 → 排字条 → 演绎 → 结算 → 下一封信/下一天 → 收集结局。
现有架构撑不起循环，因为**状态没有家**。

---

## 2. 核心原则（一切设计的出发点）

> **场景是视图，数据是真相。场景之间永不直接传数据、永不互相跳转。**

落实到 Godot 就是三条：

1. **所有游戏状态放进 autoload 单例**（当前天、每栏排列、判定结果、命运值、已解锁结局）。
   场景只负责"读状态渲染 + 把玩家操作写回状态"。
2. **场景切换由一个"流程控制器"统一路由**。任何场景都不许自己 `change_scene_to_file`，
   只能向流程控制器报告"我完成了"。
3. **判定规则进数据（JSON），不进代码**。加新关卡 = 加一个 JSON，不碰 GDScript。

---

## 3. 总体架构（分层图）

```
┌─────────────────────────────────────────────────────┐
│  Autoload 层（全局单例，永远存活）                      │
│                                                      │
│  GameState   —— 纯数据：当前天数、每栏字条序列、         │
│                 角色命运值、flags、已解锁结局           │
│                 唯一可序列化的对象（存档 = dump 它）     │
│                                                      │
│  GameFlow    —— 流程：信号总线 + 场景路由               │
│                 goto("arrange") / goto("performance") │
│                 持有"读完几封信、该去哪个场景"的进度     │
│                                                      │
│  RuleEngine  —— 纯函数：judge(序列数组) → 结局 ID      │
│                 从关卡 JSON 读判定表，不碰 UI           │
└──────────────────────┬──────────────────────────────┘
                       │ 读/写 GameState，经 GameFlow 跳转
┌──────────────────────┴──────────────────────────────┐
│  场景层（视图，互相之间零引用）                          │
│                                                      │
│  Desk 书桌       —— 信件堆总览（未读/已读/下一天）        │
│  LetterReader    —— 读信（打字机，已完成 ✅）            │
│  ArrangeBoard    —— 交换字条（scenes/arrange/arrange_board.tscn，已完成 ✅）     │
│  Performance     —— 演绎：按新顺序重放故事（新建）        │
│  Verdict         —— 结算：各角色命运/结局展示（新建）     │
│  Gallery         —— 结局图鉴（后期，原版的核心收集要素）   │
└─────────────────────────────────────────────────────┘
```

关键点：**场景之间的关联 = 全部挂在 GameFlow 上，是星型结构，不是链式结构**。
只有 2 个场景时感觉不出区别；等有 6 个场景，链式互相跳转会立刻变成乱麻。

### 三个 autoload 的职责边界

| 单例 | 管什么 | 不管什么 |
|---|---|---|
| `GameState` | 数据与读写接口；`to_dict()` / `from_dict()` 序列化 | 不知道任何场景存在 |
| `GameFlow` | 场景切换路由、流程进度（读完几封信）、对外信号 | 不存剧情数据 |
| `RuleEngine` | 序列 → 结局的匹配逻辑、verdicts 写入 | 不碰 UI、不碰场景 |

## 4. 场景流转：游戏的"主循环"

```
书桌(Desk)
   │ 点开一封信
   ▼
读信(LetterReader) ──读完发 reading_finished──▶ GameFlow 记录"此信已读"
   │                                     │
   │            本日还有信未读 ───────────┘（回书桌读下一封）
   │            本日信全部读完
   ▼
交换字条(ArrangeBoard)
   │ 点「执行」→ 把两栏序列写入 GameState → RuleEngine.judge()
   ▼
演绎(Performance)  ← 用打字机按新顺序重放黑块+字条（复用读信的打字机！）
   │
   ▼
结算(Verdict)  ← 展示各角色命运变化，解锁结局图鉴条目
   │
   ├─ 本关有多个结局想重玩 → 回 ArrangeBoard（重排再演绎）
   └─ 进入下一天 → GameState.current_day += 1 → 回书桌
```

这是原版《WILL》的骨架，也是所有新场景的"挂载点"。
其中**演绎场景是最缺的核心一环**——玩家排完字条，必须看到"重排后的故事变成什么样"，
否则拖拽没有意义。

### 场景间通信约定

- 每个场景对外**只暴露"完成"类信号**，GameFlow 统一监听：
  - `LetterReader` → `reading_finished`（已有 ✅，标准范本）
  - `ArrangeBoard` → `arrangement_submitted(sequences)`（未来）
  - `Performance` → `performance_finished`（未来）
- 任何场景都可以被单独 `F6` 调试，不会连累全局流程。
- 场景进入时从 GameState 拉数据初始化；离开前把结果写回 GameState。

## 5. 统一数据模型（两份 JSON 合成一份"天"）

现状 `letter_1.json` 与 `level_1.json` 讲同一个黑伞故事却各存一份文案——这是"场景各自为政"在数据层的体现。
建议合成"日"（day）级别的数据包：

```json
{
  "day_id": "day_01",
  "title": "黑伞",
  "characters": { "A": { "name": "角色 A", "color": "#905f80" } },

  "letters": [
    { "id": "L1", "character": "A", "pages": [ "..." ] }
  ],

  "columns": [
    {
      "id": "left",
      "character": "A",
      "blocks": [ { "id": "PanelA1", "text": "..." } ],
      "strips": [ { "id": "A1", "text": "...", "origin": "L1" } ]
    }
  ],

  "outcomes": [
    {
      "id": "true_end",
      "condition": {
        "left":  ["PanelA1", "A1", "PanelA2"],
        "right": ["PanelB1", "A2", "B1", "PanelB2"]
      },
      "verdicts": { "A": { "fate": 2, "flag": "got_umbrella" } }
    },
    { "id": "fallback", "condition": {}, "verdicts": {} }
  ],

  "next_day": "day_02"
}
```

设计说明：

- **`letters` 与 `strips` 用 `origin` 关联**——读信时读"原始信件"，交换字条时拖"信被拆成的段落"，
  演绎时按新顺序拼回去。同一故事文本只存一份。
- **`condition` 的格式 = `get_sequence_ids()` 的输出格式**（`scripts/ui/arrange/arrange_board.gd:186` 已就绪）。
  判定就是模式匹配：从上到下匹配 `outcomes`，命中即该结局。
- **`fallback` 兜底**保证任何排列都有结局（原版里乱排 = 坏结局）。
- **黑块（blocks）也应动态生成**，不依赖 `scenes/arrange/arrange_board.tscn` 里预置的 `PanelA1/PanelB1` 节点。
  新关卡完全靠 JSON 创建，两栏、三栏都行（现有 `scene_node` 字段已是朝这个方向的半步）。
- 原版一个关卡常有 1~3 封信、多角色交错，`letters` 用数组就是为此预留。

---

## 6. 判定引擎（RuleEngine）

保持**纯函数**：输入序列 → 输出结局 ID。它做三件事：

1. 按优先级从上到下匹配 `outcomes` 的 `condition`；
2. 把命中的 `verdicts`（命运值增减、flags）写进 GameState；
3. 把结局 ID 记入 GameState 的"本关已解锁结局"列表——这是结局图鉴和重玩的数据来源。

命运的数值和 flags 要**跨天持久**：原版后期有"前面某天的排法影响后面某天"的跨关卡伏笔，
所以 `verdicts` 里既有数值（fate）也有标记（flag）。

---

## 7. 存档免费获得

GameState 是纯数据单例，因此：

- 存档 = `JSON.stringify(GameState.to_dict())` 写文件；
- 读档 = 反向 `from_dict()`。

状态集中化最大的红利就是：**不需要为存档设计任何额外结构**。

## 8. 渐进改造路线（不推翻现有代码，每一步都保持可玩）

| 步骤 | 内容 | 说明 |
|---|---|---|
| 1. 立脊椎 | 新建 `scripts/game_state.gd` + `scripts/game_flow.gd` 两个 autoload，在 `project.godot` 注册；两个场景的硬编码路径改为从 GameState 取"当前天的数据"；`scripts/ui/letter/letter_reader.gd` 的硬编码跳转改为 `GameFlow.goto("arrange")` | 纯"接线"，不碰已完成的玩法逻辑 |
| 2. 合数据 | `letter_1.json` + `level_1.json` 合成 `data/days/day_01.json`（按第 5 节 schema） | 改文案从此只动一处 |
| 3. 接判定 | 实现 `RuleEngine`；`_on_execute_pressed()` 从"打印"改为"写序列 → 判定 → 跳演绎" | 序列读取函数已就绪，最顺的一步 |
| 4. 做演绎+结算 | 新场景渲染"黑块+字条按最终顺序拼接"的完整故事；**先把打字机逻辑从 `scripts/ui/letter/letter_reader.gd` 抽成可复用组件**（如 `TypewriterLabel` 或共用基类），否则演绎场景会复制 150 行打字机代码 | 让拖拽产生意义的核心一步 |
| 5. 加书桌与多天 | Desk 场景 + `current_day` 推进，形成完整循环 | 主循环闭环 |
| 6. 收尾 | 结局图鉴、存档读档、清理历史文件（`DroSlot.gd`/`DropSlot.gd`/`panel_container.tscn`/`control.tscn` 等）、按 `scenes/`、`data/days/`、`autoload/` 整理目录 | 项目长期可维护 |

## 9. 现在就可以定下的小决策

- **主场景换成书桌**：现在 `project.godot` 的 `run/main_scene` 是 `scenes/arrange/arrange_board.tscn`。
  最终游戏应从书桌/标题进入，交换字条只是流程中的一站。
- **一个场景 = 一个职责**：读信场景永远不碰拖拽，排字条场景永远不碰打字机。
  现有边界是对的，保持住。
- **场景切换只走 GameFlow**：全项目禁止出现第二个 `change_scene_to_file`。
- **内容与代码分离**：现有"黑块文字/字条内容/配色都在 JSON"的原则（README 第 1 节）继续贯彻，
  并且扩展到结局判定表。
